# KV-Cache 分叉对比

给推理工程师的小工具：从一次推理的中途分叉出多条分支，各自续写不同词元，
对比下一词元预测。内置固定权重的单层因果注意力小模型，续写复用实际算出的
KV 缓存；KV 按固定大小的物理块管理，分叉共享前缀块（写时复制），块数有上限，
网页实时显示块占用。

## 启动

```bash
docker compose up --build
# 打开 http://localhost:8000
```

不用 Docker 也可以：

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

可调参数（环境变量，compose.yaml 里有默认值）：

| 变量 | 默认 | 含义 |
|---|---|---|
| `VOCAB_SIZE` | 64 | 词表大小，词元取值 `0..63` |
| `D_MODEL` | 32 | 注意力维度 |
| `BLOCK_SIZE` | 4 | 每个物理块容纳的词元数 |
| `NUM_BLOCKS` | 32 | 物理块总数（全部会话共享的容量上限） |
| `SEED` | 1234 | 固定权重的伪随机种子 |

## 用法

1. 输入一串整数词元建会话（自动算出 KV 并写入块）；
2. 选中一条分支，在任意位置（包括块中间）分叉 —— 只共享前缀块、不新占块，池满也能分叉；
3. 给各分支追加一串词元，页面展示各自的下一词元预测（top-1 与 top-5）；
4. 关闭分支只回收引用计数归零的块；页头与块网格实时显示占用；
5. 「加入队列」提交的追加按会话公平排队：同一会话串行执行、跨会话轮转，
   开始执行前可在任务列表里取消，容量不足会留在队列等块回收后自动重试。

## 设计要点

- **模型**（`app/model.py`）：单层单头因果注意力，`x = E[tok] + P[pos]`，
  `k/v/q = x @ W_{k,v,q}`，`logits = softmax(Kq/√d)·V @ Wo`。权重由固定种子生成，
  float64。K/V 只取决于 `(token, position)`，因此缓存值与从头逐位计算完全等价。
- **块池**（`app/blocks.py`）：固定数量物理块，每块 `BLOCK_SIZE` 个槽位，
  引用计数管理共享；归零才回到空闲池。
- **引擎**（`app/engine.py`）：
  - 分叉：子分支引用前缀块并增加引用计数，不分配新块；
  - 追加：先算清所需块数（末尾共享未满块需写时复制 1 块 + 新增整块数），
    空闲不足则整体拒绝，分支内容与块占用不变；检查与提交在同一把锁内完成，
    并发追加安全；
  - 分叉点落在块内时，子分支只承认该块前 `position` 个槽位，首次写入触发写时复制；
  - 预测只读缓存的 K/V（加上末词元的 q），不重算历史。
- **API**（`app/main.py`）：`POST /api/sessions`、`POST /api/sessions/{id}/fork`、
  `POST /api/sessions/{id}/append`、`GET /api/sessions/{id}/branches/{bid}/predict`、
  `DELETE /api/sessions/{id}/branches/{bid}`、`DELETE /api/sessions/{id}`、
  `GET /api/stats`。容量不足返回 409，参数非法 400，不存在 404。

## 追加任务队列

页面上的「加入队列」按钮（接口 `POST /api/sessions/{id}/queue`，或带 `session_id`
的 `POST /api/queue`）把一次追加交给内存中的调度器：

- **同会话串行**：同一会话同时最多一条追加处于「执行中」，其余按提交顺序排队；
- **跨会话轮转**：一次只执行一个会话的队首任务，执行完该会话排到轮转队尾，
  空闲容量在各会话之间轮流使用，不会被先到的会话垄断；
- **入队后可取消**：`DELETE /api/queue/{job_id}` 只能取消尚未跨过取消边界的任务。
  取消检查与「标记已开始」在引擎锁内、分配 KV 块之前原子完成：排队中的任务立即
  取消；刚被调度取出但还没拿到引擎锁的任务登记取消意图，引擎拿到锁后直接放弃，
  不改动任何块；已经分配块的任务取消返回 400，必须整体成功或整体回滚；
- **容量不足不失败**：拿不到块时任务留在 `queued` 并标记 `waiting_capacity`，
  不计入执行次数；块被回收（关闭分支/会话）后会立即唤醒重试；
- **重启丢弃**：队列只在进程内存中，服务重启后未执行的任务全部消失。

任务状态：`queued`（排队中，可能附带 `waiting_capacity`）、`running`（执行中）、
`succeeded`（成功）、`cancelled`（已取消/重启丢弃）、`failed`（参数/对象失效
或执行异常）。页面「追加任务队列」区域展示实时队列、状态徽标、说明与取消按钮。

队列相关接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/sessions/{id}/queue` | 提交追加任务，返回 202 + 任务 |
| POST | `/api/queue` | 同上，`session_id` 放在请求体 |
| GET | `/api/queue` | 任务列表、各状态计数、执行中会话、轮转顺序 |
| GET | `/api/queue/{job_id}` | 单个任务 |
| DELETE | `/api/queue/{job_id}` | 取消尚未拿块的任务；已开始返回 400 |
| GET | `/api/queue/status` | 调度器快照（运行数、各会话排队数、轮转顺序） |

排队上限由 `MAX_QUEUED` 控制（超出返回 429），已完成任务保留 `MAX_HISTORY` 条。

## 测试

```bash
pip install -r requirements-dev.txt
pytest -v
```

覆盖：缓存路径 vs 从头计算的 logits 一致（1e-10）、块内分叉的共享与写时复制、
满池分叉、追加整体拒绝的原子性、关闭分支的精确回收、引擎内与 HTTP 层的并发容量约束；
追加队列方面覆盖同会话串行、三会话轮转、排队任务取消、取消请求与执行并发时的
取消边界、已拿块后拒绝取消、容量不足等待与回收后自动重试、目标分支/会话在排队期间
消失时记录失败、写入中途异常时引擎整体回滚、进程重启丢弃未执行任务，以及对应的
HTTP 接口与（用 jsdom 跑的）页面状态渲染。
